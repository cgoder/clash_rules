# 批判性配置评估报告

基于目标：7x24 TUN 模式稳定运行
- 目标1：国内服务非常流畅
- 目标2：国外 AI 服务非常稳健
- 目标3：代理不稳定时仍能流畅访问国内外

---

## 🚨 严重问题（会导致服务中断）

### 问题1：DNS 单点故障 - 代理挂掉后国外服务全挂
**当前配置：**
```yaml
nameserver:
  - "https://1.1.1.1/dns-query#一键代理"
  - "https://8.8.8.8/dns-query#一键代理"
```

**问题分析：**
- 所有国外域名 DNS 查询**强制走代理**
- 代理节点全部故障时，DNS 解析直接失败
- 表现：国外网站完全无法访问（不是慢，是根本打不开）

**违反目标3：** 代理不稳定时无法流畅访问国外网站

**严重程度：** ⚠️⚠️⚠️ 致命（7x24 运行不可接受）

**实际场景：**
- 凌晨3点所有代理节点维护 → ChatGPT/Claude 全部无法访问
- 订阅服务器临时故障 → 无法解析任何国外域名
- 网络抖动导致代理连接超时 → DNS 查询卡死

---

### 问题2：冷启动循环依赖风险
**当前配置：**
```yaml
default-nameserver:
  - 1.1.1.1          # 需要直连
  - 8.8.8.8

proxy-server-nameserver:
  - https://1.1.1.1/dns-query  # DoH 需要先连接
```

**问题分析：**
1. Clash 启动 → 需要解析代理服务器域名
2. 使用 `proxy-server-nameserver`（DoH）
3. DoH 需要先建立 HTTPS 连接到 1.1.1.1
4. 但 1.1.1.1 可能被 DNS 污染或封锁
5. 回退到 `default-nameserver`（明文 UDP）
6. 如果 1.1.1.1 的 UDP 53 端口也被污染 → **启动失败**

**违反目标3：** 代理不稳定/网络环境差时无法启动

**严重程度：** ⚠️⚠️ 高（部分地区/网络环境下无法冷启动）

**风险场景：**
- 路由器重启后 Clash 无法自动恢复
- 切换网络环境（家→公司→移动热点）时启动失败
- ISP 临时调整 DNS 策略导致启动卡死

---

## ⚠️ 中等问题（影响稳定性和性能）

### 问题3：Load-Balance 健康检查过于激进
**当前配置：**
```yaml
Anchor_LB:
  interval: 120              # 2分钟检测一次
  timeout: 1500              # 1.5秒超时
  max-failed-times: 2        # 2次失败即剔除
```

**问题分析：**
- 2分钟检测 × 1.5秒超时 = 极易误判网络抖动为节点故障
- 2次失败即剔除 → 短暂丢包会导致可用节点被踢出
- 在不稳定代理环境下，节点池会快速收缩

**违反目标3：** 代理不稳定时反而加剧问题

**严重程度：** ⚠️⚠️ 中等（7x24 运行会频繁误判）

**实际场景：**
- 晚高峰时段所有节点延迟波动 → 大量节点被误剔除
- 剩余节点压力增大 → 进一步超时 → 雪崩式失效
- 最终只剩1-2个节点，无法负载均衡

---

### 问题4：AI 服务缺少故障转移策略
**当前配置：**
```yaml
- {name: ChatGPT, <<: *Anchor_OP, icon: '...'}
- {name: Claude, <<: *Anchor_OP, icon: '...'}

Anchor_OP: {
  proxies: [
    一键代理,  # 默认选择
    香港负载均衡, ...
  ]
}
```

**问题分析：**
- AI 服务使用 `Anchor_OP`（手动选择组）
- 默认使用"一键代理" → 如果默认选择的区域全挂，需要手动切换
- 没有自动故障转移机制

**违反目标2：** AI 服务稳健性依赖人工干预

**严重程度：** ⚠️⚠️ 中等（无人值守时影响可用性）

**实际场景：**
- 凌晨使用 ChatGPT，香港节点全挂 → 需要醒来手动切换到美国节点
- AI 服务长时间对话中途中断 → 上下文丢失

---

### 问题5：国内服务可能被误代理
**当前配置：**
```yaml
rules:
  - RULE-SET,my_direct,国内直连
  - RULE-SET,my_proxy,一键代理
  # ... AI 服务规则
  - RULE-SET,cn_domain,国内直连
  - MATCH,漏网之鱼  # 默认走代理
```

**问题分析：**
- 国内新域名/CDN 可能不在 `cn_domain` 规则中
- 兜底规则 `漏网之鱼` 默认走代理
- 导致部分国内服务被错误代理 → 变慢或无法访问

**违反目标1：** 国内服务流畅性受影响

**严重程度：** ⚠️ 低-中（取决于规则集更新频率）

**实际场景：**
- 新上线的国内视频平台 CDN 域名走代理 → 卡顿
- 公司内网服务被误代理 → 无法访问

---

## 💡 次要问题（优化空间）

### 问题6：fake-ip 可能导致兼容性问题
**当前配置：**
```yaml
dns:
  enhanced-mode: fake-ip
  fake-ip-filter:
    - 'stun.*.*'
    - '+.xboxlive.com'
    - '+.speedtest.net'
```

**问题分析：**
- fake-ip 模式在部分应用中有兼容性问题（如银行APP、游戏客户端）
- 虽然有 `fake-ip-filter`，但可能不完整
- 7x24 运行中可能遇到未预期的应用故障

**严重程度：** ⚠️ 低（但难以调试）

---

### 问题7：缺少 DNS 查询降级机制
**当前配置：**
没有配置 DNS fallback 策略

**问题分析：**
- 如果主 DNS（1.1.1.1 via 代理）失败，没有备用方案
- Clash 内部会回退，但没有显式配置可能导致不可预期行为

**严重程度：** ⚠️ 低（Clash 有内部保护）

## 🔧 关键改进建议

### 改进1：DNS 降级策略（最优先）
**目标：** 代理挂掉时仍可解析国外域名

**方案A：混合路由（推荐）**
```yaml
nameserver:
  - "https://1.1.1.1/dns-query#一键代理"
  - "https://8.8.8.8/dns-query#一键代理"
  - "https://1.1.1.1/dns-query#DIRECT"  # 降级备用
```

**方案B：智能回退**
```yaml
nameserver:
  - "https://1.1.1.1/dns-query#RULES"  # 恢复自动判断
```

**权衡：**
- 方案A：代理挂时自动降级，但可能泄漏部分 DNS 查询
- 方案B：放弃完全防泄漏，换取稳定性

---

### 改进2：放宽健康检查参数
```yaml
Anchor_LB:
  interval: 300              # 5分钟（原120秒）
  timeout: 3000              # 3秒（原1500ms）
  max-failed-times: 5        # 5次（原2次）
```

**效果：** 减少误判，提高节点池稳定性

---

### 改进3：AI 服务使用 fallback 策略
```yaml
- name: ChatGPT
  type: fallback
  proxies:
    - 美国负载均衡    # 优先
    - 香港负载均衡    # 降级
    - 台湾负载均衡    # 再降级
  url: 'https://chat.openai.com'
  interval: 300
```

**效果：** 自动故障转移，无需人工干预

---

### 改进4：兜底规则改为直连
```yaml
rules:
  # ... 现有规则
  - MATCH,国内直连  # 从"漏网之鱼"改为直连
```

**效果：** 未知国内域名不会被误代理

---

## 🎯 推荐的优先级

1. **立即修复（严重问题）：**
   - DNS 降级策略（改进1方案A或B）
   - 放宽健康检查参数（改进2）

2. **短期优化（中等问题）：**
   - AI 服务自动故障转移（改进3）
   - 兜底规则改为直连（改进4）

3. **长期监控（次要问题）：**
   - 观察 fake-ip 兼容性
   - 定期更新国内域名规则集

---

## 💭 防泄漏 vs 稳定性权衡

**当前配置：** 极端防泄漏（10/10）+ 低稳定性（3/10）
**建议配置：** 实用防泄漏（7/10）+ 高稳定性（9/10）

**核心观点：**
- 7x24 运行中，**可用性 > 完全防泄漏**
- 允许降级时的部分 DNS 泄漏，换取服务不中断
- 米家 WebRTC 已经泄漏本地 IP，DNS 泄漏的增量风险较小

**建议策略：**
- 正常运行时：完全防泄漏（DNS 走代理）
- 代理故障时：自动降级直连 DNS（可用性优先）
- 通过监控及时发现降级事件
