## 🎯 针对不稳定性的设计建议

### 策略1：区域级负载均衡（推荐）⭐
```yaml
# 每个区域内所有节点负载均衡
香港负载 (13个节点) ← Load-Balance
台湾负载 (8个节点) ← Load-Balance
美国负载 (5个节点) ← Load-Balance
```

**优势**：
- ✅ 单节点故障只影响 1/N 的连接
- ✅ 充分利用所有节点带宽
- ✅ 自动容错，无需手动切换

---

### 策略2：全局负载均衡
```yaml
# 所有节点（42个）全部加入一个负载均衡池
全球负载 (42个节点) ← Load-Balance
```

**优势**：
- ✅ 最大化容错能力
- ✅ 最大化带宽利用

**劣势**：
- ❌ 延迟不可控（可能走到很远的节点）
- ❌ 不适合延迟敏感场景

---

### 策略3：混合策略（最优）⭐⭐⭐⭐⭐
```yaml
# 区域负载均衡 + 服务分类
proxy-groups:
  # 区域负载均衡池
  - 香港负载 (LB, 13节点)
  - 台湾负载 (LB, 8节点)
  - 美国负载 (LB, 5节点)
  
  # 服务级策略
  - 一键代理 (select) → 选择区域
  - ChatGPT → 美国负载
  - YouTube → 香港负载
  - 国内直连 → DIRECT
```

## 📋 健康检查参数建议

### 针对不稳定服务器优化
```yaml
load-balance:
  interval: 120          # 2分钟检测一次（缩短）
  timeout: 1500          # 1.5秒超时（降低）
  max-failed-times: 2    # 2次失败即剔除（快速）
  lazy: false            # 主动检测，不惰性
```

**原理**：
- 快速检测故障节点
- 快速剔除故障节点
- 减少对用户的影响
