# 🚀 Load-Balance 配置使用指南

## 📋 配置概览

**文件名**：`clashmi_LB.yml`  
**设计目标**：专门针对不稳定代理服务器的负载均衡配置  
**核心策略**：Load-Balance（负载均衡）  

---

## 🎯 核心特性

### 1️⃣ 全面负载均衡策略
```yaml
# 区域级负载均衡
香港负载均衡 (13个节点) ← Load-Balance
台湾负载均衡 (8个节点)  ← Load-Balance
美国负载均衡 (5个节点)  ← Load-Balance
新加坡负载均衡 (3个节点) ← Load-Balance
日本负载均衡 (1个节点)  ← Load-Balance
欧洲负载均衡 (8个节点)  ← Load-Balance
其他负载均衡 (5个节点)  ← Load-Balance
```

**优势**：
- ✅ 单节点故障只影响 1/N 的连接
- ✅ 自动分散风险，无需手动切换
- ✅ 充分利用所有节点带宽
- ✅ 快速容错，2次失败即剔除

---

### 2️⃣ 针对不稳定服务器的优化参数

```yaml
Anchor_LB: &Anchor_LB {
  type: load-balance,
  strategy: consistent-hashing,  # 保持会话一致性
  interval: 120,                 # 2分钟检测（比标准300秒更快）
  lazy: false,                   # 主动检测，不惰性
  timeout: 1500,                 # 1.5秒超时（快速判断故障）
  max-failed-times: 2,           # 2次失败即剔除（比标准3次更快）
}
```

**对比标准配置**：

| 参数 | 标准配置 | 不稳定优化 | 提升 |
|------|----------|------------|------|
| interval | 300秒 | 120秒 | ⚡ 快 2.5倍 |
| timeout | 2000ms | 1500ms | ⚡ 快 25% |
| max-failed-times | 3次 | 2次 | ⚡ 快 33% |
| lazy | true | false | ⚡ 主动检测 |

---

### 3️⃣ 自动排除信息节点

```yaml
filter: "^(?!.*(剩余流量|距离下次重置|套餐到期|去除.*线路|跳转域名|请勿连接)).*$"
```

**自动排除**：
- ❌ `剩余流量：1514 GB`
- ❌ `距离下次重置剩余：22 天`
- ❌ `套餐到期：2026-07-24`
- ❌ `去除4条不合适线路`
- ❌ `跳转域名{请勿连接}:nflink.info`

---

### 4️⃣ 备用最快节点组

```yaml
# 如果负载均衡不满意，可切换到最快节点
香港最快 ← URL-Test（自动选择最快节点）
台湾最快 ← URL-Test
美国最快 ← URL-Test
```

## 🔧 使用方法

### 步骤1：导入订阅

在 `clashmi_LB.yml` 顶部添加你的订阅链接：

```yaml
proxy-providers:
  NCloud:
    <<: *Anchor_PR
    url: "你的订阅链接"
    path: ./proxies/NCloud.yaml
```

- Clash Verge Rev：重载配置
- FlClash：重启应用

### 步骤3：选择策略组

**推荐设置**：
```
一键代理 → 香港负载均衡
```

**备用设置**（如果负载均衡延迟不理想）：
```
一键代理 → 香港最快
```

## 💡 Load-Balance 工作原理

### consistent-hashing 策略

```yaml
strategy: consistent-hashing
```

**工作流程**：
```
1. 用户访问 google.com
   ↓
2. hash("google.com") % 13 = 5
   ↓
3. 使用 HKG F 节点
   ↓
4. 再次访问 google.com → 仍然是 HKG F
   ↓
5. 访问 youtube.com → hash("youtube.com") % 13 = 2 → HKG B
```

**特点**：
- ✅ 相同域名走相同节点（保持登录状态）
- ✅ 不同域名走不同节点（分散负载）
- ✅ 节点故障自动切换到其他节点

### 实际效果

**场景1：1个节点掉线**
```
Fallback: 所有连接中断，等待切换
Load-Balance: 只影响该节点的连接（7.7%），其他连接正常
```

**场景2：5个节点不稳定**
```
Fallback: 频繁切换，体验极差
Load-Balance: 自动剔除故障节点，剩余8个节点继续工作
```

**场景3：下载大文件**
```
Fallback: 单节点带宽（假设10MB/s）
Load-Balance: 多节点并行（理论最高130MB/s）
```

## ⚠️ 注意事项

### 1. Load-Balance 不适合的场景

#### ❌ 游戏（需要稳定低延迟）
**问题**：不同连接走不同节点，延迟不一致  
**解决方案**：切换到"香港最快"或手动选择特定节点

#### ❌ 视频会议（需要持续低延迟）
**问题**：节点切换可能影响通话质量  
**解决方案**：切换到"香港最快"

#### ❌ WebSocket 长连接
**问题**：频繁切换影响连接  
**解决方案**：使用"香港最快"或手动选择节点

---

### 2. 单服务器多端口的风险

#### 台湾区域（8个节点，1个服务器）
```
所有节点都在: orbittwcn01.orbit5cloud.com
```

**风险**：
- ⚠️ 如果该服务器挂了，所有台湾节点失效
- ⚠️ Load-Balance 仍然有效，但会切换到其他区域

**缓解方案**：
```yaml
一键代理 → 选择多个区域的混合策略
  fallback: [香港负载均衡, 台湾负载均衡, 美国负载均衡]
```

---

### 3. 健康检查频率

**当前配置**：每 120 秒检测一次

**如果节点非常不稳定，可以调整**：
```yaml
interval: 60  # 1分钟检测一次（更激进）
```

**注意**：检测频率太高会增加服务器压力

## 🔍 故障排查

### 问题1：连接速度慢
**原因**：可能走到了延迟高的节点  
**解决方案**：
1. 切换到"香港最快"
2. 手动选择特定节点
3. 在"全部节点"中测试各节点延迟

### 问题2：某些网站打不开
**原因**：负载均衡分配的节点可能被墙  
**解决方案**：
1. 检查 Clash 日志
2. 切换到其他区域负载均衡
3. 手动选择节点

### 问题3：频繁断连
**原因**：节点确实很不稳定  
**解决方案**：
1. 降低 `max-failed-times` 到 1（更激进剔除）
2. 缩短 `interval` 到 60秒（更快检测）
3. 联系服务商更换节点

## 📋 总结

### ✅ 适合使用 Load-Balance 的情况

1. ✅ 代理服务器非常不稳定
2. ✅ 有多个节点（至少3个以上）
3. ✅ 一般浏览、下载、上传场景
4. ✅ 需要充分利用带宽
5. ✅ 不希望频繁手动切换节点

### ⚠️ 需要切换到"最快节点"的情况

1. ⚠️ 游戏（延迟敏感）
2. ⚠️ 视频会议（稳定性要求高）
3. ⚠️ WebSocket 长连接
4. ⚠️ 对延迟抖动敏感的应用
