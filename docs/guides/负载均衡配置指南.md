# 🚀 负载均衡配置指南

> 针对不稳定代理服务器的负载均衡优化配置

## 📋 概述

**配置文件**：`clashmi_LB.yml` / `clashmi.yml`  
**核心策略**：Load-Balance（负载均衡）  
**适用场景**：代理节点不稳定、需要充分利用多节点带宽

---

## 🎯 核心优势

### 负载均衡策略
```yaml
香港负载均衡、台湾负载均衡、新加坡负载均衡、日本负载均衡、美国负载均衡
香港速度优先、台湾速度优先、新加坡速度优先、日本速度优先、美国速度优先
```

**优势**：
- ✅ 单节点故障只影响 1/N 的连接
- ✅ 自动分散风险，无需手动切换
- ✅ 充分利用所有节点带宽
- ✅ 快速容错，自动剔除故障节点

---

## ⚙️ 负载均衡参数

### 针对不稳定服务器的优化
```yaml
Anchor_LB: &Anchor_LB {
  type: load-balance,
  strategy: consistent-hashing,  # 保持会话一致性
  interval: 300,                 # 健康检查间隔
  lazy: false,                   # 主动检测
  timeout: 3000,                 # 3秒超时
  max-failed-times: 5,           # 5次失败剔除
}
```

### 速度优先参数
```yaml
Anchor_UT: &Anchor_UT {
  type: url-test,
  interval: 300,
  lazy: true,                    # 惰性检测
  tolerance: 100,                # 100ms 容差
  timeout: 2000,
  max-failed-times: 3,
}
```

## 💡 工作原理

### consistent-hashing 策略（推荐）
```
访问 google.com → hash("google.com") % 节点数 = 节点5
再次访问 google.com → 仍然是节点5（保持会话）
访问 youtube.com → hash("youtube.com") % 节点数 = 节点2
```

**特点**：
- ✅ 相同域名走相同节点（保持登录状态）
- ✅ 不同域名走不同节点（分散负载）
- ✅ 节点故障自动切换

### round-robin 策略（轮询）
```
连接1 → 节点1
连接2 → 节点2
连接3 → 节点3
连接4 → 节点1（循环）
```

**特点**：
- ✅ 绝对平均分配
- ⚠️ 可能影响会话一致性
- ✅ 适合下载场景

## ⚠️ 注意事项

### Load-Balance 不适合的场景

#### ❌ 游戏（需要稳定低延迟）
**问题**：不同连接走不同节点，延迟不一致  
**解决方案**：切换到"速度优先"或手动选择特定节点

#### ❌ 视频会议（需要持续低延迟）
**问题**：节点切换可能影响通话质量  
**解决方案**：切换到"速度优先"

#### ❌ 金融服务（需要固定 IP）
**问题**：IP 频繁变化可能触发风控  
**解决方案**：手动选择固定节点

## 🔍 故障排查

### 连接速度慢
**原因**：走到了延迟高的节点  
**解决**：
1. 切换到"速度优先"
2. 手动选择特定节点
3. 查看日志确认节点状态

### 某些网站打不开
**原因**：分配的节点可能被封  
**解决**：
1. 检查 Clash 日志
2. 切换到其他区域负载均衡
3. 手动选择可用节点

### 频繁断连
**原因**：节点确实很不稳定  
**解决**：
1. 降低 `max-failed-times` 到 2（更快剔除）
2. 缩短 `interval` 到 180秒（更快检测）
3. 联系服务商更换节点
