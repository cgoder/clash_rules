# 负载均衡 vs 故障转移策略对比

> 选择适合你的代理策略

## 📊 策略概览

### Fallback（故障转移）
```yaml
type: fallback
proxies: [节点A, 节点B, 节点C]
```
**特点**：优先使用第一个可用节点，故障时切换到下一个

### Load-Balance（负载均衡）
```yaml
type: load-balance
strategy: consistent-hashing
proxies: [节点A, 节点B, 节点C]
```
**特点**：多个连接分散到不同节点，充分利用资源

---

## 🔍 工作原理对比

### Fallback 工作流程
```
初始状态
    ↓
使用节点A（所有连接）
    ↓
节点A失败3次
    ↓
切换到节点B（所有连接）
    ↓
节点B失败3次
    ↓
切换到节点C
```

**特点**：
- 同一时间只用一个节点
- 故障时集体切换
- 优先级明确

### Load-Balance 工作流程
```
初始状态
    ↓
连接1 → 节点A
连接2 → 节点B
连接3 → 节点C
连接4 → 节点A（循环）
    ↓
节点B故障
    ↓
只有连接2受影响，自动重试其他节点
其他连接不受影响
```

**特点**：
- 多节点同时工作
- 故障影响局部
- 自动容错

## 📈 性能对比

### 延迟稳定性

| 策略 | 延迟 | 稳定性 | 评分 |
|------|------|--------|------|
| Fallback | 低（单节点） | ⭐⭐⭐⭐⭐ | 适合游戏/会议 |
| Load-Balance | 中（多节点平均） | ⭐⭐⭐ | 适合浏览/下载 |

### 容错能力

| 策略 | 故障影响 | 恢复速度 | 评分 |
|------|---------|---------|------|
| Fallback | 所有连接中断 | 慢（需健康检查） | ⭐⭐⭐ |
| Load-Balance | 仅部分连接 | 快（即时重试） | ⭐⭐⭐⭐⭐ |

### 带宽利用

| 策略 | 利用率 | 峰值带宽 | 评分 |
|------|--------|---------|------|
| Fallback | 单节点 | 单节点带宽 | ⭐⭐ |
| Load-Balance | 多节点并行 | 多节点总和 | ⭐⭐⭐⭐⭐ |

### 不稳定环境适应性

| 策略 | 节点波动 | 频繁故障 | 评分 |
|------|---------|---------|------|
| Fallback | 频繁切换 | 体验差 | ⭐⭐ |
| Load-Balance | 自动剔除 | 影响小 | ⭐⭐⭐⭐⭐ |

## 🎯 适用场景

### Fallback 最佳场景

#### ✅ 游戏
**需求**：稳定低延迟  
**原因**：
- 单节点连接，延迟一致
- 避免延迟波动影响操作
- 保持游戏会话稳定

#### ✅ 视频会议
**需求**：持续稳定连接  
**原因**：
- 避免节点切换导致卡顿
- 保持音视频流畅
- 降低丢包率

#### ✅ 节点质量差异大
**需求**：优先使用最优节点  
**原因**：
- 有明确的"最快节点"
- 次优节点仅作备用
- 不需要负载分散

---

### Load-Balance 最佳场景

#### ✅ 节点不稳定
**需求**：容错能力  
**原因**：
- 单节点故障影响小（1/N）
- 自动剔除故障节点
- 不需要手动切换

**对比效果**：
```
假设10个节点，1个掉线

Fallback: 100% 连接中断，需等待切换
Load-Balance: 10% 连接受影响，其他正常
```

#### ✅ 下载/上传大文件
**需求**：充分利用带宽  
**原因**：
- 多节点并行传输
- 总带宽 = 节点数 × 单节点带宽
- 提升传输速度

**对比效果**：
```
假设单节点 10MB/s，10个节点

Fallback: 最高 10MB/s
Load-Balance: 理论最高 100MB/s
```

#### ✅ 高并发浏览
**需求**：分散请求负载  
**原因**：
- 多个网页请求并行
- 不同域名走不同节点
- 避免单节点过载

#### ✅ 节点质量相近
**需求**：无明显最优节点  
**原因**：
- 所有节点延迟相近
- 无需优先级排序
- 充分利用所有资源

## 🔬 实际场景分析

### 场景1：1个节点掉线

#### Fallback 表现
```
使用节点A
    ↓
节点A掉线
    ↓
所有连接中断
    ↓
等待300秒健康检查
    ↓
切换到节点B
    ↓
恢复服务（中断5分钟）
```

#### Load-Balance 表现
```
连接1,2,3 → 节点A
连接4,5,6 → 节点B
连接7,8,9 → 节点C
    ↓
节点A掉线
    ↓
连接1,2,3 即时重试 → 节点B/C
其他连接不受影响
    ↓
服务持续（无感知切换）
```

**结论**：Load-Balance 胜出（容错能力强）

---

### 场景2：游戏对战

#### Fallback 表现
```
所有游戏包走节点A
    ↓
延迟稳定：30ms ± 2ms
    ↓
游戏体验：⭐⭐⭐⭐⭐
```

#### Load-Balance 表现
```
包1 → 节点A（30ms）
包2 → 节点B（50ms）
包3 → 节点C（35ms）
    ↓
延迟波动：30-50ms
    ↓
游戏体验：⭐⭐（延迟不稳定）
```

**结论**：Fallback 胜出（延迟稳定）

---

### 场景3：下载大文件

#### Fallback 表现
```
单节点下载
    ↓
速度：10MB/s（单节点带宽）
    ↓
下载1GB文件：100秒
```

#### Load-Balance 表现
```
10个节点并行下载
    ↓
速度：50MB/s（多节点总和）
    ↓
下载1GB文件：20秒
```

**结论**：Load-Balance 胜出（带宽利用率高）

---

### 场景4：5个节点频繁波动

#### Fallback 表现
```
节点A用5分钟 → 掉线
切换到节点B用3分钟 → 掉线
切换到节点C用7分钟 → 掉线
切换到节点D用2分钟 → 掉线
...频繁切换，体验极差
```

#### Load-Balance 表现
```
10个节点工作
    ↓
节点A掉线 → 自动剔除，影响10%连接
节点B掉线 → 自动剔除，影响11%连接
节点C掉线 → 自动剔除，影响12%连接
    ↓
剩余7个节点继续工作
影响范围：累计33%连接（已自动恢复）
```

**结论**：Load-Balance 胜出（不稳定环境适应性强）

## 🎮 策略选择指南

### 决策树
```
你的主要场景是什么？
    │
    ├─ 游戏/视频会议 → Fallback（或 URL-Test）
    │
    ├─ 节点经常掉线 → Load-Balance
    │
    ├─ 下载/上传大文件 → Load-Balance
    │
    ├─ 有明显最快节点 → Fallback（或 URL-Test）
    │
    └─ 一般浏览/开发 → Load-Balance
```

### 混合配置（推荐）⭐
```yaml
proxy-groups:
  # 游戏/会议专用
  - name: 低延迟
    type: url-test           # 或 fallback
    proxies: [节点A, 节点B]
  
  # 一般场景
  - name: 香港负载均衡
    type: load-balance
    strategy: consistent-hashing
    proxies: [HK01, HK02, HK03, ...]
  
  # 顶层选择
  - name: 一键代理
    type: select
    proxies: [香港负载均衡, 低延迟, ...]
```

## 📊 总结表

| 维度 | Fallback | Load-Balance | 推荐场景 |
|------|----------|--------------|---------|
| **延迟稳定性** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | 游戏/会议 → Fallback |
| **容错能力** | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 不稳定节点 → LB |
| **带宽利用** | ⭐⭐ | ⭐⭐⭐⭐⭐ | 下载 → LB |
| **不稳定适应** | ⭐⭐ | ⭐⭐⭐⭐⭐ | 频繁故障 → LB |
| **配置复杂度** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 简单 → Fallback |
| **资源利用率** | ⭐⭐ | ⭐⭐⭐⭐⭐ | 高并发 → LB |

### 最终建议

#### 选择 Fallback/URL-Test 如果：
- ✅ 延迟敏感（游戏/会议）
- ✅ 有明显最优节点
- ✅ 节点质量稳定

#### 选择 Load-Balance 如果：
- ✅ 节点经常不稳定
- ✅ 需要高带宽（下载）
- ✅ 节点质量相近
- ✅ 高并发场景

#### 混合配置（最佳实践）：
- ✅ 根据不同场景分别配置
- ✅ 顶层策略组可手动切换
- ✅ 兼顾延迟和容错能力
